# Blazing Pizza

A port of the app from Microsoft's [Blazor workshop](https://github.com/dotnet-presentations/blazor-workshop):
the specials with a pizza configurator, a checkout with validation, sign-in, and the orders with a live
delivery map. It is a test vehicle for the framework; what the port found is in
[docs/port-findings.md](../../docs/port-findings.md).

## Running

The app needs its backend, `server/server.mjs`. It re-implements the workshop's ASP.NET Core server
(`BlazingPizza.Server`) in plain Node, with the same REST contract and no dependencies.

Once, in the repository root:

```sh
pnpm install
pnpm --filter "blazing-pizza^..." build   # the @tsazor packages the app uses
```

Then, in two terminals:

```sh
pnpm --filter blazing-pizza api   # the backend on http://localhost:5300
pnpm --filter blazing-pizza dev   # the app on http://localhost:5301
```

Open http://localhost:5301 and sign in as `test@example.com` / `test1234`, or register a new user.
Browsing the specials works without signing in. Checkout and the orders require it (`@authorize`).

- **The proxy:** Vite's dev server forwards `/specials`, `/toppings`, `/orders`, `/notifications` and
  `/auth` to the backend (`vite.config.ts`). The app calls its API on its own origin, like the workshop's
  `HttpClient` with its `BaseAddress`. Without the backend, the app still starts, but it shows no pizzas.
- **The store is in memory:** a restart of the backend empties it; the seed user stays.
- **An order's status:**
  - *Preparing* for 10 s;
  - then *Out for delivery* for 60 s, while the driver moves across the map;
  - then *Delivered*.

  The order page polls every 4 s.

The production build:

```sh
pnpm --filter blazing-pizza build     # tsazor check + vite build → dist/
pnpm --filter blazing-pizza preview   # dist/ on http://localhost:4173, with the same proxy
```

The backend has to run for the preview as well.

## Tests

```sh
pnpm --filter blazing-pizza test     # the order status engine (node --test)
pnpm --filter blazing-pizza verify   # end to end, in headless Edge
```

`verify` walks the whole flow:
1. registers a user and orders a pizza;
2. tries the checkout's validation;
3. checks the order page (status, the Leaflet map, the polling);
4. checks MyOrders;
5. logs out and back in.

It also requires zero console errors. It reuses a backend or dev server that already runs on its port,
and starts and stops the missing ones itself. `TSAZOR_BROWSER=firefox` or `webkit` runs it in the other
engines. Like CI's browser jobs, it is written for Windows (Edge, `taskkill`).

## The API client

`src/api/` holds a client generated by [`@tsazor/dotnet`](../../packages/dotnet/README.md) from the
checked-in contract `src/api/openapi.json`. It returns `HttpResult` values instead of throwing.

```sh
pnpm --filter blazing-pizza exec tsazor-dotnet generate src/api/openapi.json --out src/api --name PizzaApi
```

This writes `models.ts` and `pizza-api.ts`. The contract is written by hand, because the Node backend has
no Swashbuckle. With an ASP.NET Core backend it would be its `swagger.json`. A change to the backend's
endpoints means a change to `openapi.json` and running the generator again.

## Structure

| Part | Contents |
|---|---|
| `src/Pages/` | `Index` (the specials), `Checkout`, `MyOrders`, `OrderDetails`, `Login`, `Register` |
| `src/components/` | `ConfigurePizzaDialog`, `ConfiguredPizzaItem`, `OrderReview`, `AddressEditor`, `Map` (imports Leaflet from npm directly, no JS interop), `Poller` |
| `src/OrderState.ts` | The current order (the cart and the pizza being configured), a DI service as in the workshop |
| `src/AuthProvider.ts` | The `AuthenticationStateProvider` over the backend's cookie session |
| `src/OrdersClient.ts` | The orders API on top of the generated client |
| `server/server.mjs` | The backend: seed data, the in-memory store, the order status engine, cookie sessions |
| `wwwroot/` | The workshop's static files (CSS, fonts, images); Vite's `publicDir` |
| `scripts/verify-pizza.mjs` | The end-to-end gate |
| `test/` | Unit tests for the status engine |

## Deviations from the workshop

Details and reasons are in [port-findings.md, section D](../../docs/port-findings.md#d-documented-deviations-from-the-original).

| Workshop | This port |
|---|---|
| Backend | Node with an in-memory store, not ASP.NET Core with EF/SQLite |
| Sign-in | A cookie session (`/auth/register`, `login`, `logout`, `user`), not ASP.NET Identity with OIDC |
| Push notifications | Not ported. The subscribe endpoint exists but only keeps the subscription in memory. |
| GraphQL specials (module 6) | Not ported |
