The user's question was: "What about scoped CSS and source files like in Blazor (AddressEditor.tsazor.ts / AddressEditor.tsazor.css)?"

### 1. Scoped CSS (`X.tsazor.css`) — recommendation: build first

Blazor mechanism 1:1: markup emission gets a scope attribute `b-<hash>` (hash deterministic from the file path), the CSS rewriter appends `[b-<hash>]` to every compound selector (`.a > .b:hover` → `.a[b-x] > .b[b-x]:hover`), `@media` is traversed, `@keyframes` untouched. `::deep` as in Blazor: the attribute only on selectors *before* the `::deep`, then a descendant combinator (`[b-x] .child`). Injection via `import "./X.tsazor.css"` in the codegen — Vite handles dev/build.

- Runtime share: none. Compiler share: one emission change.
- The actual effort: a robust selector rewriter → **postcss as a dependency** (instead of regex) proposed.

### 2. Code-behind (`X.tsazor.ts`) — afterwards ~~(open)~~ → **done 2026-09-29**

TS has no partial classes → mapped via inheritance:
`X.tsazor.ts` exports `export default class XCode extends ComponentBase {...}` (declares its own `extends`, also @inherits chains: generated → code-behind → base). The compiler detects `X.tsazor.ts` next to `X.tsazor`, imports the default export, emits `extends`.

- **Verified for free on the runtime side**: `findParameterMetadata` (packages/runtime/src/components/parameter-metadata.ts:33) already walks the prototype chain → `@Parameter()` in the code-behind class works today.
- Document the deviation from Blazor: no `partial`, a visible base class.
