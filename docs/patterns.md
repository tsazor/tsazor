# Architecture patterns

How to structure a Tsazor app that grows past a handful of pages. Nothing here is enforced by the
framework; it is the structure the framework is built for, and what the tutorial teaches piece by
piece. If you know Blazor: almost all of it carries over unchanged — the differences are named.

## Layers

```text
Pages            @page components: routing, composition, loading data          src/Pages/…
Feature UI       components of one feature (forms, lists, dialogs)              src/Features/<feature>/…
Shared UI        design-system components (@tsazor/fluent, @tsazor/bootstrap, your own)
Services         state and use cases, plain TypeScript classes, via DI           src/Features/<feature>/*.ts
Backend client   typed HTTP client generated from the backend's OpenAPI          src/Api/… (@tsazor/dotnet)
```

Dependencies point down only: a page uses feature components and services; a service never
imports a component; the backend client knows nothing of either. Components stay thin — markup,
parameters, events — and the logic lives in services and plain functions, where it is testable
without rendering anything.

## Feature folders

Group by feature, not by kind. One folder per feature holds its pages' building blocks, its
services and its tests:

```text
src/
  _Imports.tsazor            @using ./Shared, @using @tsazor/fluent, common @imports
  App.tsazor                 Router, layout, error boundary
  Program.ts                 createTsazorApp: services, routes
  Shared/                    layout, navigation, small shared components
  Pages/
    Orders/                  @page "/orders", @page "/orders/{id:int}"
    Admin/                   lazy (see Lazy loading)
  Features/
    Orders/
      _Imports.tsazor        @using ./ for the feature's own components
      OrderList.tsazor
      OrderEditor.tsazor
      OrderState.ts          service: the feature's state and use cases
      order-rules.ts         pure functions (pricing, validation helpers)
      OrderList.test.ts
  Api/
    orders-client.ts         generated by @tsazor/dotnet from the backend's OpenAPI
```

`_Imports.tsazor` files cascade down the folders (Blazor's `_Imports.razor`), so a feature folder
declares its `@using`s once. Pages may also live inside their feature folder; keep them where the
team finds them — the router does not care, the `@page` directive is the route.

## Services via DI

A service is a plain TypeScript class, registered in `Program.ts` and injected with `@inject`
(Blazor's `builder.Services.Add…` and `@inject`):

```ts
// Program.ts
createTsazorApp({
  root: App,
  routes,
  services: (services) => {
    services.registerValue(TsazorHttp, new TsazorHttp({ baseUrl: "/api" }));
    // Factories resolve their dependencies; singleton is the default lifetime.
    services.register(OrdersClient, (s) => new OrdersClient(s.get(TsazorHttp)));
    services.register(OrderState, (s) => new OrderState(s.get(OrdersClient)));
    // registerType(T) constructs `new T(services)` — for classes that take the provider.
    services.registerType(OrderDraft, { lifetime: "transient" });
  },
});
```

- **Lifetimes:** in the browser there is one app, so *singleton* is the normal case (Blazor
  WebAssembly's *scoped* behaves the same). Use *transient* for short-lived helpers; *scoped* only
  with explicit scopes (`createScope()`).
- **Shared state** belongs in a service, not in a cascading value: components `@inject` it and call
  `this.observe(service)` to re-render on its changes (any object with `subscribe(listener)` works —
  a store, an RxJS subject, your own class). Tsazor addition: Blazor has no `observe`; there you
  call `StateHasChanged` from an event handler.
- **Cascading values** are for context that belongs to a subtree (a theme, the form's
  `EditContext`, the auth state) — not for app state.
- **No service locator** in components: inject what you use; it is what makes the fake in a test
  possible.

## Containers and presentational components

Split a component when it does two jobs:

- A **container** (often the page) loads data, holds state, talks to services.
- A **presentational** component renders what it gets through parameters and reports through
  `EventCallback`s. It does not inject services; it is reusable and trivial to test.

```tsazor
@* OrderRow.tsazor — presentational *@
@import { formatMoney } from "./order-rules"
@import type { Order } from "../../Api/orders-client"

<tr>
    <td>@order.number</td>
    <td>@formatMoney(order.total)</td>
    <td><button @onclick="() => onCancel.invokeAsync(order)">Cancel</button></td>
</tr>

@code {
    @Parameter() order!: Order;
    @Parameter() onCancel!: EventCallback<Order>;
}
```

Two-way parameters of your own components use `@Bindable()` (Tsazor extension; it generates the
`value`/`valueChanged` pair Blazor writes by hand), so callers can write `@bind-value`.

## Where code lives

- **Markup + a small `@code` block** — the default. Fields are state; getters are derived values.
- **Code-behind** (`OrderEditor.tsazor.ts`, a class the component extends; see
  [code-behind.md](code-behind.md)) when the `@code` block outgrows the markup, when tooling or
  reviews favor plain `.ts`, or for a shared base class.
- **Plain modules** (`order-rules.ts`) for anything that does not need the component: calculations,
  formatting, validation helpers, mapping DTOs. They are the cheapest code to test and reuse —
  prefer them over logic in components.
- **Services** for state that outlives a component or is shared, and for use cases that call the
  backend.

Rule of thumb: if a function does not touch `this`, it does not belong in the component.

## Talking to the backend

Generate the client from the backend's OpenAPI document with `@tsazor/dotnet` (one contract for
backend and frontend; DTO changes become compile errors), register it as a service, and handle
results explicitly:

```ts
const result = await this.orders.createOrder(draft);
if (result.ok) this.created = result.body;
else this.error = problemMessage(result);   // ASP.NET ProblemDetails, validation errors included
```

`TsazorHttp` (or plain `fetch`) works too — the typed client is a choice, not a requirement. Keep
HTTP out of components: the service calls the client, the component calls the service.

## Forms

`EditForm` with a model class carrying validation attributes (`@Required()`, `@StringLength()` …,
Blazor's DataAnnotations), `DataAnnotationsValidator`, `ValidationMessage`. Use one model per form
(not the DTO itself, when the form differs from the payload); map it in the service. Rules that need
other fields or services go into a `ModelValidator` (the tutorial's "Rules with context") — not into
the component.

## Localized text: store keys, not strings

Text that is *stored* — navigation entries, menu items, labels kept in a service or a data model —
does not change language when the culture switches: it was translated once, when it was stored.
The framework re-renders components that use the `StringLocalizer`, but it cannot re-translate a
string you kept. So store the **key** and translate at render:

```ts
// in the service: keys
readonly menu = [{ href: "orders", labelKey: "Menu.Orders" }, { href: "admin", labelKey: "Menu.Admin" }];
```

```tsazor
@foreach (const item of Nav.menu) {
    <NavLink Href="@item.href">@L.get(item.labelKey)</NavLink>
}
```

The trap shows up only on a culture switch at runtime — everything looks right until a user
changes the language and half the screen stays in the old one.

## Errors

- An `ErrorBoundary` around the router's content (in the layout) keeps one failing page from taking
  down the app; feature-level boundaries isolate widgets.
- HTTP failures are values (`HttpResult`), not exceptions, in the generated client; show them where
  the user acted.
- `OnNavigateAsync` failures reach the router's boundary.

## Testing

- **Plain modules and services:** ordinary Vitest tests — no rendering, no DOM.
- **Components:** `@tsazor/testing` — `render(Component, { parameters, services })`, then `find`,
  `click`, `change`, `markup` (bUnit-style). Replace services with fakes through `services`; that is
  why components inject instead of constructing.
- **Pages and flows:** a few browser tests (Playwright) for the critical paths.

```ts
const view = await render(OrderList, {
  services: (services) => services.registerValue(OrderState, fakeOrderState([order])),
});
await view.click("button.cancel");
expect(view.findAll("tr")).toHaveLength(0);
```

## Lazy loading

Load rarely used features on demand: `tsazor({ lazyRoutes: ["src/Pages/Admin/**"] })` makes their
pages separate chunks loaded on the first visit (the router shows `<Navigating>` meanwhile). Split
by feature, not page by page across the app: the start page and the everyday features stay eager.
See the routing section of the [language reference](language-reference.md#lazy-routes-tsazor-extension).

## Auth

The browser never holds the decision: `AuthorizeView` and `@authorize` shape the UI, the server
enforces access. The recommended setup is a BFF with an HttpOnly cookie — see [auth.md](auth.md).

## Checklist for a new feature

1. A folder under `src/Features/<feature>` with its `_Imports.tsazor`.
2. A service for its state and use cases; registered in `Program.ts`.
3. Pages that compose feature components; feature components that take parameters and raise
   events.
4. Logic in plain modules; tests for those and for the service.
5. Component tests with fake services for the parts with behavior.
6. `lazyRoutes` if the feature is large and not used on every visit.
