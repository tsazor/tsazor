# Port: FluentCMS → Tsazor

**Status:** started 2026-10-08. This is the main track before 1.0.

**Why.** A real Blazor app shows whether Tsazor's API is complete and stable, and gives practical
experience with it.
- Every gap the port finds becomes a framework fix with a test, logged below. The port is the vehicle;
  the framework is the subject ([port-findings.md](port-findings.md) holds the earlier ports).
- **The 1.0 signal:** a week of porting with no change to the public API (`api/*.api.d.ts`) means the
  API can freeze. A release candidate follows.

**The original.** [FluentCMS](https://github.com/fluentcms/FluentCMS) (MIT), commit `c63d49c`
(2025-09-20, the latest on `dev`).
- A Blazor Web App on .NET 9: static SSR with InteractiveServer islands. One process hosts the REST
  API and the UI.
- The UI calls the API over HTTP, through clients NSwag generates.
- Data lives in LiteDB, a single file, so no database server is needed.

## Architecture of the port

1. **Backend: upstream FluentCMS, unchanged.** `scripts/backend.mjs`:
   - clones the pinned commit;
   - runs it on `:5000` with its own data directory;
   - runs the first-time setup through the API.
2. **BFF: an ASP.NET Core project in `apps/fluentcms/bff`** (YARP).
   - **Why:** FluentCMS's API wants two credentials on every call: the app's API token (`X-API-AUTH`)
     and the user's JWT. The Blazor Server UI keeps both on the server; an SPA cannot keep a secret.
   - **What it does:**
     - it holds the API token and adds it to every proxied call;
     - it keeps the JWT in an HttpOnly cookie and adds it as `Bearer`;
     - it serves `/auth/login`, `/auth/user` and `/auth/logout`, the pattern of [auth.md](auth.md).
   - This is the API-boundary step every Blazor Server team meets when it moves to an SPA.
3. **API client:** generated by `@tsazor/dotnet` from the checked-in `src/api/openapi.json`
   (`--envelope data,errors`).
4. **Page model as in the original:**
   - a catch-all page resolves the URL through `Page.GetByUrl`;
   - the page's sections render their plugins through `DynamicComponent`, each in an `ErrorBoundary`;
   - sub-screens are the same plugin under another view name (`?pluginId=…&viewName=…`).
5. **Layouts:** the seeded layouts (Admin, Auth) become Tsazor layout components with Fluent. Every other
   layout is the HTML stored in the CMS, rendered as it is (`Shell/StoredLayout.tsazor`, phase 5).
6. **Forms:** the static SSR forms (`[SupplyParameterFromForm]`, `FormName`, `Enhance`) become interactive
   `EditForm`s. `@rendermode` goes away (TZS warning, no effect in an SPA).

**Phase 5: the question it asks.** A FluentCMS layout is HTML in the database. A component tag in it
(`<PluginsSection Name="Main" fluentcms />`) names a component, its attributes are the parameters, and
Scriban expressions (`{{ user.user_name }}`) are filled in first. Blazor renders it with
`RenderTreeBuilder` at run time: HTML segments as `MarkupString`, each tag through `OpenComponent`
with a type found by reflection. So the question is: **can a Tsazor app turn markup it only gets at run
time into a render tree with live components, without a compiler in the browser?**

- Blazor's segments only work because static SSR streams them as text. In an SPA, each `MarkupString`
  is parsed alone, so a `<main>` opened before a component and closed after it would not contain it.
  The port parses the whole layout once and builds elements down to each component.
- No reflection: the component tags resolve through a registry, the pattern of the plugins.
- Scripts in the layout: the original runs them on a full page load and raises `fluentcms:init`, then
  `fluentcms:afterenhanced` after each enhanced navigation. The port loads each script once and raises
  the same events.
- Out of scope: the site builder (design mode: the preview in an iframe, drag and drop, each plugin's settings,
  edit and data dialogs, the admin toolbar; 10 files), the inline editor, the Tailwind style builder. Its one
  capability that is new to the port, a sortable list (drag and drop with a keyboard way), is a track B candidate.

**Codemod, per screen** (`tsazor codemod` over the original `.razor` files):

| Screen | Files | Automatic fixes | Left by hand |
|---|---|---|---|
| Roles | 3 | 0 | The library's components (20 tags), `@rendermode`, a C# anonymous object (`new { id = … }`), the code-behind (C#), DTO members in PascalCase (`context.Name` → `context.name`) |
| Users | 3 | 0 | The same; the static SSR forms (three on one view) become three interactive ones |

The codemod helps little when the component library is swapped: the markup's tags and parameters are the library's. A port that keeps its library would show what it can do.

**Method, per screen:**
1. Run the codemod over the original files and record what compiles as it is.
2. Port the screen, and record what had to change by hand.
3. Fix every framework gap at its root, with a test, and log it below.

**Running it:**

```sh
pnpm --filter fluentcms backend   # FluentCMS on :5340 (clones and builds it the first time, sets it up)
pnpm --filter fluentcms bff       # the BFF on :5341
pnpm --filter fluentcms dev       # the app on :5342
pnpm --filter fluentcms verify    # end to end; starts what isn't running
```

Sign in as `admin` / `Admin123!`. A plugin that isn't ported yet shows "… is not ported yet" in its place.

## Track B: complex components

Complex components are a port of their own (owner, 2026-10-08): a library author must be able to build them
with Tsazor, or the framework has a gap.

**The purpose is the proof, not the components** (owner): track B makes sure complex components *can* be
built; better components are a side effect.
- **Choosing:** a component is next when it tests a capability nothing has proven yet (the second column).
  Whether FluentCMS needs it decides the order among those, not the choice. A second component that asks for
  the same capability adds nothing.
- **Done means:** the capability is proven by a test; the component is honest (keyboard, axe), and every
  gap it hit is fixed in the framework. Feature parity with Fluent UI Blazor is not a goal.
- **Reference:** the complex components of Microsoft's Fluent UI Blazor (MIT), the Blazor counterpart of
  `@tsazor/fluent`. The question for each one: can its API and behavior be built in Tsazor?
- **Placement:** the logic goes in `@tsazor/ui`, the Fluent skin comes first, with tests and axe. Bootstrap
  follows when its skin needs the component, not to prove the capability twice.

**Notes from phase 3**
- A component that raises two bound callbacks in a row (`folderChanged`, then `parentFoldersChanged`) must pass
  the new values, not its fields: the parent re-renders after the first callback and hands the child its old
  value of the second. Blazor behaves the same. `FilesTable.load()` shows the pattern.
- The port's folder picker shows the API's error (`File.AlreadyExists`, a folder moved into itself); FluentCMS's
  own had no place for it.

**Notes from phase 5**
- **The answer to its question is yes.** The capability needed no framework change; only Blazor 8's name for one
  builder call was missing (F37), and the docs didn't show the technique (F36). A layout parsed once into
  elements, markup and component tags builds through the public `RenderTreeBuilder` (`Shell/layout-markup.ts`). Components work
  in the head part too (`PageHead`, inside `HeadContent`). Sequence numbers come from a node's place among its
  siblings, and all of an element's attributes share one, so a changed text keeps the components.
- **Upstream as the oracle.** The backend process also serves FluentCMS's own Blazor UI, for a request with the
  site's host. So the verify script compares each public plugin's HTML with FluentCMS's own render, character
  for character, and a small proxy with that host (`:5343`) drives FluentCMS's UI in a browser (U3, U4). The
  Scriban subset's expected values come from Scriban 5.12 itself, run on the same templates. That found what a
  reading of the templates wouldn't: FluentCMS's API client makes a `DateTime` of every string that parses as
  one, Scriban writes it as `09 Jun 2024`, and it indents a block's lines by the spaces before its statement.
- **What the checks didn't see, a person did (F38).** Every check compared content: the HTML matched
  upstream's, the head had its stylesheets. That the head's elements were thrown away and added again on
  every navigation was visible only as a flicker. A C# rule the runtime relied on without saying so
  (delegate equality) had no JS counterpart. Checks that a navigation keeps the DOM's elements belong next to
  checks of what it shows.
