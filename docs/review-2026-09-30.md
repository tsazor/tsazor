# Review — Stand 2026-09-30

Gesamt-Review von Compiler, Runtime, Tooling/Komponenten-Libraries plus ein mechanischer
Kompatibilitäts-Scan über alle 217 `.razor`-Dateien von
[FluentCMS](https://github.com/fluentcms/FluentCMS) (als Testvehikel, nicht als Portierungsziel).
Befunde sind — sofern nicht als *unverifiziert* markiert — per Scratch-Test/-Skript belegt.
Stand der Codebasis: Commit `0abdc98` (+ untracked `apps/fluentcms-admin`).

**Kurzfazit:** Die Architektur (RenderTree/Renderer/Komponentenmodell, Shadow-Module +
TS-LanguageService im LSP) trägt; Sequenznummern sind sauber. Vier strukturelle Themen
erzeugen aber fast alle Einzelbefunde:

1. Compiler rät auf Textebene statt zu parsen.
2. Kein Typecheck, keine Parameter-Typ-Metadaten.
3. Runtime-Diff und -Batching sind nicht Blazors Algorithmus.
4. Import-Auflösung per Heuristik.

### Befunde (hoch — Blazor-Porting-Lücken)

- **C11** `@switch`-Fallthrough (`case B:\ncase C:`) → `case B: { break; }` (parser.ts:386-409, codegen.ts:900-913).
- **C12** Statische Komponenten-Attributwerte sind immer Strings: `Count="5"` → `"5"`, `OnClick="Handle"` → `"Handle"` (parser.ts:620, codegen.ts:693). In Razor sind das C#-Ausdrücke, typisiert durch den Parameter.
  *Nachtrag (Phase 0):* Auch `Interval="@4000"` wird zum String `"@4000"` — `@` + Ziffer ist
  keine implizite Expression und bleibt still literal. Im Pizza-Port führte das zu
  `setInterval(fn, "@4000")` ⇒ 0 ms ⇒ **~1200 `GET /orders/{id}` in 5 s**, unbemerkt vom E2E.
  App-seitig auf `@(4000)` korrigiert; der Pizza-E2E prüft jetzt die Polling-Rate.
- **C13** Keine benannten Slots / `RenderFragment<T>` / `@context` / `Context=` / `TItem=` (codegen.ts:664-670) — Slot-Tags werden als Komponenten aufgelöst.
- **C14** Unquoted Attribute: `<input type=checkbox disabled>` → `checkbox=""`, `type` verloren (parser.ts:786-790).
- **C15** `@onclick:preventDefault="cond"` / `:stopPropagation="true"` erzeugt einen zweiten Handler (parser.ts:659-670). Modifier ohne Handler ist Fehler (Blazor erlaubt es).
- **C16** `@bind-Value:after/:get/:set` auf Komponenten abgelehnt (parser.ts:716-723).
- **C17** `@bind-Value="Model!.Title"` abgelehnt — `isAssignableTarget` (codegen.ts:928) kennt `!.` nicht. **77 % aller FluentCMS-Compile-Fehler.**
- **C18** Method-Groups auf fremden Objekten verlieren den Receiver: `@onclick="item.toggle"` → wird mit Komponente als `this` gerufen (event-callback.ts:48).
- **C19** Direktiven:
  - `@attribute` dokumentiert, aber kein Codegen-Case (codegen.ts:140-173) → TZS001 **und** wörtlich über die Klasse geschrieben.
  - Mehrere `@page` → letzte gewinnt still.
  - `@typeparam T where T : class` wörtlich in `class C<…>`.
  - **`@namespace` / `@rendermode` / `@implements` / `@preservewhitespace` werden als Content gerendert** (FluentCMS: `@namespace` in 160/217 Dateien).
  - Generisches `@inherits Base<ICollection<T>>` → ungültiger Import `import Base<…> from "./Base<…>"` (FluentCMS: 24 Dateien).
  - `@page`/`@code` innerhalb von Elementen still gedroppt bzw. zu Render-Statements.
- **C20** `@:`-Zeilen verarbeiten keine `@`-Transitionen (parser.ts:200-208).
- **C21** Ein im `@code` selbst geschriebenes `buildRenderTree` wird still vom generierten (leeren) überschrieben.

### Befunde (mittel/niedrig)

- `<input></input>` → „Missing closing tag" (parser.ts:478/495); `<DIV>` als Komponente (parser.ts:469); `a < b` im Text → TZS002; `{ json }` in Component-ChildContent → TZS003.
- `class="btn @(cond ? "on" : null)"` → `"btn null"` (Blazor: leer).
- Einzeilige Blöcke emittieren Whitespace-Textframes pro Iteration.
- `@for (var i …) { <Row>@i</Row> }` — `var` in deferred ChildContent-Lambda ⇒ alle Rows zeigen den Endwert (`let` emittieren löst das).
- Abweichende `@foreach`-Header (`Person p in people`, `var (k, v) in pairs`) → Fallback + ungültiges TS.
- Sourcemap-Spalten in `@code` falsch (Tabs → 2 Spaces vor Spaltenberechnung), `sourcesContent: null`.

### Positiv

**Sequenznummern sind korrekt:** compile-time Counter (codegen.ts:335-345), deterministisch,
quellpositionsgebunden, Loop-Iterationen teilen Nummern, Branches haben disjunkte Bereiche,
ChildContent-Lambdas starten in eigener Region bei 0.

### Empfehlung

1. **`bakeMemberRefs` durch TS-AST + Scope-Analyse ersetzen** (`ts.createSourceFile` —
   TypeScript ist bereits Dependency). Nur Identifier umschreiben, die tatsächlich Member
   sind (aus dem `@code`-Klassenkörper + Basisklasse via Checker); alles andere bleibt frei
   (Import/Global). Macht `knownGlobals` und den Basisklassen-Workaround (port-findings C)
   überflüssig.
2. **Code-first-Parser in Code-Kontexten** (wie Razor): TS-Statements via `ts.createScanner`,
   Wechsel zu Markup bei `<tag` in Statement-Position, `@:`, `<text>`. Dann funktionieren
   `while`/`do`/`try`/`using`/Fallthrough ohne Sonderknoten, Locals sind im Scope, der
   Brace-Pre-Scan entfällt.
3. **Zeilenbewusster Code-Writer** (oder magic-string mit Token-Mappings) für korrekte Sourcemaps.
4. **Diagnose für jedes unbekannte `@wort` am Statement-Anfang** und für `@` nach
   Alphanumerik — fängt einen Großteil der stillen Fehler. Die Doku-Aussage „scheitert nie
   still" stimmt derzeit nicht.

## 2. Typsicherheit: kein Typecheck, keine Parameter-Metadaten

- **T1** Der Build strippt nur Typen (esbuild `transformSync`, vite-plugin/src/index.ts:126). Kein `tsazor check` (Backlog, handoff-2026-09-28.md:98).
- **T2** Komponenten-Parameter werden nicht geprüft — auch nicht im LSP: `b.addAttribute(1, "Name", 123)` mit `unknown`. `<Greeter Name="@(123)" Nmae="typo"/>` → 0 Diagnostics. Fluent-d.ts ist `export const X: any`.
- **T3** Runtime verwirft unbekannte Parameter still (component-base.ts:67-76); Blazor wirft.
- **T4** Cross-File-Typen nur, wenn die andere Datei im Editor offen ist (ts-service.ts / server.ts:79). False Positive: `<Greeter @ref="g"/>` → TS2740.
- Was der LSP fängt: Member-Tippfehler im Markup, Fehler im `@code`.

**Belege aus dem fluentcms-Port** (beide Build-grün, beide Laufzeitfehler):
- `apps/fluentcms-admin/src/RedirectToLogin.tsazor:6` ruft `this.nav.navigateTo`, das Feld heißt `this.Nav` (`@inject NavigationManager Nav`, codegen.ts:258).
- Dieselbe Datei definiert `buildRenderTree` im `@code` → wird vom generierten leeren überschrieben (C21), rendert nichts.

**Empfehlung (höchster Hebel):** Shadow-Module aus `packages/lsp` erweitern — typisierte
Prop-Prüfung pro Komponenten-Tag (z. B. `satisfies Partial<ParamsOf<Greeter>>`), Shadows auch
für geschlossene Dateien, `tsazor check`-CLI (+ optional Vite-Hook), echte `.d.ts` pro
Komponente. Die **Parameter-Typ-Metadaten** sind zugleich Voraussetzung für C12
(statische Attribute, Method-Groups), C13 (Templated Components) und `TItem`-Inferenz.

## 3. Runtime: Diff und Batching nicht Blazor-getreu

### Kritisch

- **R1 `@key`-Wechsel erzeugt nichts neu** (diff.ts:358-394): Key-Miss fällt ins Sequenz-Matching → dieselbe Instanz bekommt `setParameters`, dasselbe DOM-Element. Bricht „Key ändern = Reset".
- **R2 Doppelte Keys verschmelzen DOM** (diff.ts:358-366): zwei `<p @key=1>` → ein `<p>`. Blazor wirft.
- **R3 Komponenten in entfernten Elementen werden nie disposed** (dom-renderer.ts:374-381, 192-195). Leakt `addLocationChanged`-Subscriptions (NavLink, Router), EditContext, Auth — leaked Komponenten rendern bei jeder Navigation in detached DOM. Gleiches bei Tag-Wechsel. *Vermutlich der folgenreichste Praxisbug.*
- **R4 Verschieben von Markup-Block/Komponente verschiebt nur die Kommentar-Marker** (dom-renderer.ts:557-564, 588-594). Wird derzeit durch R8 kaschiert.
- **R5 `ShouldRender() === false` verhindert den ersten Render** (renderer.ts:196). Blazor rendert initial immer.
- **R6 Async-Lifecycle** (component-base.ts:40-46): `onInitialized` und `onParametersSet` werden awaited, `stateHasChanged` einmal am Ende ⇒ **kein Loading-State**. Blazor rendert, wenn der Task noch läuft, und erneut nach Abschluss. `architecture.md` („rendert nach jedem await-Abschnitt") und `port-findings.md` #3 („rendert nicht nach dem await", „Blazor verhält sich identisch") sind **beide falsch**. Das „hängt im Loading"-Symptom aus dem Pizza-Port stammt vermutlich von Fire-and-forget-Aufrufen (*unverifiziert*).
- **R7 Parent-`onAfterRender(firstRender)` läuft vor dem Child-Render**: beobachtet `P.render, P.after, K.render, K.after`.

### Hoch

- **R8 Keine Parameter-Change-Detection** (dom-renderer.ts:298): jeder Parent-Render re-rendert den ganzen Teilbaum, `OnParametersSet` feuert jedes Mal. `attributeValueEquals` (diff.ts:416) ist toter Code.
- **R9 Render-Queue** (renderer.ts:187-226): Reihenfolge nach Einfügung statt Parent-first (Child rendert doppelt); Renders während Flush → neuer Microtask; ein Throw in `buildRenderTree` verwirft den Rest des Batches (uncaught). Kein ErrorBoundary.
- **R10 Attribute** (dom-renderer.ts):
  - :432-435 Handler auf `null` → Listener bleibt aktiv.
  - :453-456 `checked` als Attribut statt Property → Checkbox synchronisiert nach User-Klick nicht mehr (trifft `InputCheckbox`, `@bind` auf Checkbox).
  - :197-198 `<select value>` vor den `<option>`s gesetzt → Initialwert falsch (trifft `InputSelect`).
  - :458-459 `name in element` weist getter-only Properties zu (`form`, `list`) → TypeError bricht Flush ab.
  - :465-476 Entfernen von `value` leert `input.value` nicht.
  - :438 Handler-Map-Lookup per Attributname vs. Eventname → Listener wird bei jeder Callback-Änderung neu gebunden.
- **R11** Runtime-`CascadingValue` ignoriert `Name` (components/cascading-value.ts:386-401).
- **R12** Cascading-Updates laufen nur über Parameter-Re-Sets (renderer.ts:125-147) → Zwischenkomponente mit `ShouldRender=false` stoppt das Update.
- **R13** `disposeAsync` wird nie gerufen (renderer.ts:150-165); Children vor Parent disposed. (FluentCMS: 44 Verwendungen.)
- **R14 Router** (route-data.ts):
  - :369-378 keine Präzedenz — `/users/{id}` schlägt `/users/new`.
  - :427 `^true|false$` ungruppiert → `/f/trueish` matcht `{b:bool}` (gleiches bei `regex(a|b)`).
  - :331 „True" matcht, konvertiert aber zu `false`.
  - Keine optionalen Parameter (`{id:int?}`); `double`/`decimal`/`float`/`datetime` → `.*`; `long` via `parseInt` verliert Präzision > 2^53; Catch-all re-encoded.
- **R15** Navigation-Lock wirkungslos (navigation-manager.ts:42-78); `baseUri` ignoriert `<base href>`; `app.dispose()` (app.ts:173) entfernt weder DOM noch Listener.

### Mittel/niedrig

- `/^on/i` macht jeden Funktions-Parameter mit „on"-Präfix (z. B. `onlyIf`) zum EventCallback und bindet an den falschen Receiver (renderer.ts:14, 108).
- Globaler `activeRenderer` (dom-renderer.ts:27, 36, 520) → bei zwei Renderern verpasst `waitUntilIdle` Handler.
- Auth-Race: später `getState()`-Result überschreibt neuere Notification (authentication-state-provider.ts:273-281).
- EditForm: `onValidSubmit` weder awaited noch getrackt; kein `OnSubmit`/`OnInvalidSubmit` (edit-form.ts:173).
- DI ohne Scoped-Lifetime und ohne Zyklus-Erkennung. `Dispatcher` ungenutzt, `isRenderingInProgress` immer false.

### Performance

- Ein Insert verschiebt alle Folgegeschwister (dom-renderer.ts:577): 1 Insert vorne in 100er-Liste = 101 `insertBefore`. **Verliert dabei Fokus** (verifiziert), vermutlich auch iframes/Video/Animationen.
- `getFrameChildren` 3× pro Element und Render, plus 4 Maps, 2 Sets, 1 Array pro Element.
- `findParameterMetadata` baut bei jedem `setParameters` eine Map über die Prototyp-Kette (renderer.ts:113, component-base.ts:50) — mit R8 für jedes Child bei jedem Parent-Render.
- Kein O(n²) im Diff selbst.

### Empfehlung

1. **`RenderTreeDiffBuilder` getreu portieren:** geordneter Zwei-Zeiger-Walk, Key-Dictionary nur als Fallback, Fehler bei doppelten Keys. Behebt R1, R2 und die Move-Kosten.
2. **Logical-Node-Range-Abstraktion** (Start/End, bewegt sich als Einheit, Removal läuft den Teilbaum ab und disposed). Behebt R3, R4.
3. **Echte Render-Queue mit Batch-Ende:** Parent-first, `OnAfterRender` nach dem ganzen Batch, erster Render ignoriert `ShouldRender`, Fehler pro Komponente isoliert → Basis für ErrorBoundary.
4. **Reihenfolge beachten:** R8 (Change-Detection) erst nach bzw. zusammen mit R4 und R12 einbauen — R8 kaschiert beide.
5. **Lifecycle-Konformitäts-Testsuite**, die Blazors Semantik festschreibt (siehe auch §7 Doku-Drift).

## 4. Import-Auflösung per Heuristik (vite-plugin / workspace)

- **I1** `knownGlobals` (vite-plugin/src/index.ts:78-81) matcht jedes Wort, das in `RUNTIME_TYPES` vorkommt: `@Parameter() Token` + `@Token` → `import { Token } from "@tsazor/runtime"` (type-only Export ⇒ Link-Fehler). PascalCase-Parameter sind Blazor-Konvention; `RouteData`, `EditContext` kollidieren.
- **I2** Importierte Namen im Markup werden `this.`-präfixiert: `@Status.Open` (Enum aus `utils.ts`) → `this.Status.Open`. Lowercase-Funktionen/Konstanten werden nie importiert.
- **I3** Default- vs. Named-Import aus dem Dateinamen geraten (resolver.ts:247-250). `plugin.test.ts:101` erwartet `import CounterService from …` gegen ein Fixture mit `export class CounterService {}` (Zeile 54) — der Test sichert einen Link-Fehler ab. Der fluentcms-Port fügt defensiv `export default FluentAuthProvider` hinzu.
- **I4** Sobald ein Bare-`@using` (npm-Paket) im Scope ist, wird jeder Tag-Name als dort exportiert angenommen (resolver.ts:242-243, 268-270) → `<Buton>` kein TZS005. Bei `@tsazor/components` + `@tsazor/fluent` gewinnt still die erste Quelle für gemeinsame Namen (Button, Card, Alert, Table, Tabs, Pagination).
- Dass False Positives meist nicht schaden, liegt nur daran, dass esbuild ungenutzte Imports entfernt — fragil, nicht sicher.

**Empfehlung:** echte Top-Level-`import`-Statements in `.tsazor` erlauben (analog Svelte
`<script module>`), oder freie Identifier über den TS-Checker im Shadow auflösen; nicht
aufgelöste/mehrdeutige Namen als Fehler melden.

## 5. Tooling, Paketierung, Komponenten-Libraries

### HMR / Invalidierung

`vite-plugin/src/index.ts` hat kein `handleHotUpdate`, keinen Watcher, kein `addWatchFile`/`invalidateModule`:
- neu angelegte Komponente → abhängige Datei bleibt auf TZS005 bis zum nächsten Edit,
- `_Imports.tsazor`-Änderung re-transformiert nichts,
- Hinzufügen/Entfernen von `.tsazor.css`/`.tsazor.ts` wirkt nicht (`docs/scoped-css.md` behauptet das Gegenteil),
- neue `@page` → Manifest veraltet (dokumentiert).

### Paketierung (extern per Tarball getestet)

- `tsc` mit `moduleResolution: bundler` emittiert endungslose Imports ⇒ extern funktioniert `vite build`, aber **Vitest + `@tsazor/testing` scheitert** (`Cannot find module …/dist/render-tree/render-tree`); `compiler`/`workspace`/`lsp` nicht direkt in Node ladbar. Fix: `module: NodeNext` + `.js`-Endungen oder pro Paket bundeln.
- Keine mitgelieferten Ambient-Types für `*.tsazor` / `virtual:tsazor-routes` — vier Apps kopieren `src/types.d.ts`, alle Komponenten als `ComponentBase` typisiert. Vorschlag: `@tsazor/vite-plugin/client`.
- `components`/`fluent` ohne `types`-Export, d.ts ist `any`.
- `packages/vscode/package.json` listet `@tsazor/lsp`/`@tsazor/workspace` nicht ⇒ **sauberes `pnpm -r build` scheitert** an vscode.
- `vite-plugin` bundelt compiler+workspace, listet sie aber als Dependencies. Kein Paket hat ein `license`-Feld.

### LSP

Design ist richtig (v2: ein `ts.LanguageService` über virtuelle Shadow-Module, v1-Regex als Fallback). Grenzen:
- nur `workspaceFolders[0]` mit dessen tsconfig — im Monorepo die Root-Solution-tsconfig (`files: []`) (ts-service.ts:105-127, server.ts:290); weicht vom Vite-Root für `_Imports` ab,
- kein `didChangeWatchedFiles`, keine Re-Checks abhängiger offener Dokumente,
- Diagnostic-Ranges 1 Zeichen breit.

### Windows-Pfade (*unverifiziert*)

`workspace/src/imports.ts:114` vergleicht `current.startsWith(stop)` case-sensitiv —
Laufwerksbuchstaben-/Case-Abweichung zwischen `config.root` und Module-ID würde den
`_Imports`-Walk nach dem ersten Ordner stoppen. `routes.ts` scannt das ganze Projekt-Root
(inkl. `test/`, `wwwroot`) statt nur `src`.

### Fluent

- `Button` deklariert `ariaLabel`/`ariaDescribedBy`, rendert sie nicht (Button.tsazor:1) → Icon-Buttons ohne Accessible Name; keine `@attributes`-Weitergabe (`data-testid`, `aria-*` gehen verloren).
- TextInput/Select/Checkbox ohne `id` → `label for` null; alle Message-IDs `fui-input-message` → doppelte IDs, kaputtes `aria-describedby`. Jede Feldmeldung `role="alert"` (laut).
- Enum-artige Parameter als `string`, inkonsistentes Vokabular („medium" vs „m"); camelCase statt PascalCase (Runtime matcht case-insensitiv, LSP schlägt camelCase vor).
- Solide: Dialog, Tabs, Toast (Focus-Trap, Roving Tabindex, `aria-live`).

### Test-Lücken

vite-plugin 19 Tests in einer Datei, workspace 6, components 22. Nicht getestet:
Invalidierung/HMR, Windows-Pfade, voller `vite build`, Import-Inferenz-False-Positives/-Negatives,
Paket-Konsum von außen. Das Plugin-Test-Fixture enthält C# (`private string summary = "Sunny"`).

## 6. FluentCMS als Kompatibilitätsmessung

**Setup:** FluentCMS ist eine Blazor Web App — statisches SSR, `InteractiveServer` per
Komponente (26 `@rendermode`), Cookie-Auth über `HttpContext` (37 Stellen / 9 Dateien),
Catch-all `@page "/{**Route:nonfile}"`, Plugins per `DynamicComponent`. 172 Dateien haben
`.razor.cs`-Code-behind, nur 1 `@code` ⇒ Markup-Befunde sind sauber von C# getrennt, und
Tsazors `X.tsazor.ts`-Modell passt direkt.

**Mechanischer Lauf** (Parser + Codegen über alle 217 Dateien):
- 171/217 ohne Diagnostic; 180 Fehler in 46 Dateien; 0 Crashes.
- Nach Abzug der stillen Fehlkompilierungen: **nur 17/217 wirklich korrekt**; mit ignoriertem `@namespace` wären es 103.

| Ursache | Vorkommen / Dateien |
|---|---|
| `@bind-Value="Model!.X"` abgelehnt (C17) | 139 von 307 Binds / 33 (77 % aller Fehler) |
| `@* *@` (C8) | 6 / 5 |
| Unquoted Attribute (C14) | 10 / 6 |
| C#-Statements in `@if`-Body (C1) | 2+ |
| `@attribute` (C19) | 1 |
| `<!DOCTYPE html>` (nur SSR-Host-Page, irrelevant) | 1 |

**Stille Fehler:** unbekannte Direktiven als Content (`@namespace` 160, `@rendermode` 26),
Slots als Komponenten (+ `@context` → `this.context`), Modifier-mit-Wert als zweiter Handler,
generisches `@inherits` (24), `new Foo()` → `new this.Foo()`.

### Konstrukt-Inventar

Aufwand: XS < 1 h · S ≈ ½–1 Tag · M = Tage · L ≥ 1 Woche.

| Konstrukt | FluentCMS | Tsazor | Aufwand |
|---|---|---|---|
| `@namespace` / `@rendermode` / `@implements` | 160 / 26 / 0 Dateien | fehlt, still | XS (ignorieren + Warnung für unbekannte) |
| `@bind-X` auf Komponenten | 304 / 67 | ja, außer `!.` | XS |
| Benannte Slots, `RenderFragment<T>`, `@context`, `Context=` | Slots 32/17, `@context` 120/15–18 | fehlt („Phase 2") | M–L (braucht Param-Metadaten) |
| `@typeparam` / generisches Code-behind | 12/8, 11 Klassen | ja, außer generisches `@inherits` | S |
| `DynamicComponent` | 9/7 (Kern des Plugin-Renderings) | fehlt | S |
| `ErrorBoundary` | umschließt jedes Plugin | fehlt (renderer.ts:294 nur `console.error`) | M |
| `HeadContent` / `HeadOutlet` / `FocusOnNavigate` | 4 / 1 / 1 | fehlt (`PageTitle` vorhanden) | S |
| `InputFile` / `IBrowserFile` | 3 / 8 | fehlt | S |

## 7. Strategisch

1. **Typecheck ist der Kern des .NET-Versprechens.** Ein .NET-Entwickler erwartet, dass
   `dotnet build` bei `<Greeter Name="@123"/>` scheitert. Die Maschinerie existiert zu großen
   Teilen im LSP (§2).
2. **Templated Components sind die größte Paritätslücke** — blockieren idiomatisches
   `App.razor` (`<Found>`), jedes DataGrid, und erzwingen heute handgeschriebenen
   `RenderTreeBuilder`-Code (gallery Table `rowContent`, fluentcms `App.tsazor`). Wichtiger
   als neue Komponenten.
3. **Die .NET-Brücke ist noch kein Framework-Feature.** Jede App erfindet ihre eigene:
   Sleipnir (externes `sleipnir-codegen`, alle Properties optional mangels Nullability),
   FluentCMS (handkopierte DTOs, Envelope pro Methode wiederholt, `openapi-typescript`-Skript
   vorhanden aber ungenutzt; `TsazorHttp` wirft bei `!ok` bevor der Envelope lesbar ist),
   Pizza (handgeschriebenes REST). Ein offizielles Paket — OpenAPI → TS-Client + Nullability
   + ProblemDetails/Envelope-Fehler + DataAnnotations → Validatoren — wäre das eigentliche
   Alleinstellungsmerkmal.
4. **Paketierung ist nicht bereit für externe Nutzer** (§5).
5. **Doku-Drift:** Lifecycle (`architecture.md` vs. `port-findings.md` #3 vs. Code),
   HMR/Sidecar-Invalidierung (`scoped-css.md`), `@attribute` (`language-reference.md`),
   „scheitert nie still". Eine Konformitäts-Testsuite sollte die Blazor-Semantik festschreiben.

## 8. Empfohlene Reihenfolge

1. **Quick Wins** (je XS):
   - `@namespace`/`@rendermode`/`@implements`/`@preservewhitespace` akzeptieren + ignorieren; **Diagnose für unbekannte `@wort`** (C19).
   - `isAssignableTarget` um `!.` erweitern (C17).
   - Event-Modifier mit Wert korrekt behandeln (C15).
   - `@attribute` im Codegen (C19).
   - Eigenes `buildRenderTree` erkennen/als Fehler melden (C21).
   - Import bei generischem `@inherits` reparieren (C19).
   - Dev-Warnung für unbekannte Parameter (T3).
   - `vscode`-Dependencies ergänzen (§5).
2. **Compiler-Umbau:** TS-AST + Scope-Analyse, Code-first-Parser, zeilenbewusster Writer (§1).
3. **Parameter-Typ-Metadaten → `tsazor check` → Templated Components** (§2, C12, C13).
4. **Runtime:** Diff-Port + Logical Ranges + Render-Queue mit Batch-Ende; danach Change-Detection; dann ErrorBoundary, DynamicComponent, DisposeAsync (§3).
5. **Paketierung** (NodeNext, Ambient-Types, echte Komponenten-d.ts) und **.NET-Bridge-Paket** (§5, §7).
