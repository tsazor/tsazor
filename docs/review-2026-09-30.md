# Review — State as of 2026-09-30

Overall review of the compiler, runtime, tooling/component libraries plus a mechanical
compatibility scan across all 217 `.razor` files of
[FluentCMS](https://github.com/fluentcms/FluentCMS) (as a test vehicle, not as a port target).
Unless marked *unverified*, findings are backed by a scratch test/script.
Codebase state: commit `0abdc98` (+ untracked `apps/fluentcms-admin`).

**Summary:** The architecture (RenderTree/Renderer/component model, shadow modules +
TS LanguageService in the LSP) holds up; sequence numbers are clean. But four structural issues
produce almost all individual findings:

1. The compiler guesses at the text level instead of parsing.
2. No type check, no parameter type metadata.
3. Runtime diff and batching are not Blazor's algorithm.
4. Import resolution by heuristic.

---

## 1. Compiler: regex-/markup-first instead of TS-AST/code-first

### Findings (critical — mostly *silent* miscompilation)

### Findings (high — Blazor porting gaps)

- **C11** `@switch` fallthrough (`case B:\ncase C:`) → `case B: { break; }` (parser.ts:386-409, codegen.ts:900-913).
- **C12** Static component attribute values are always strings: `Count="5"` → `"5"`, `OnClick="Handle"` → `"Handle"` (parser.ts:620, codegen.ts:693). In Razor these are C# expressions, typed by the parameter.
  *Addendum (Phase 0):* `Interval="@4000"` also becomes the string `"@4000"` — `@` + digit is
  not an implicit expression and silently stays literal. In the Pizza port this led to
  `setInterval(fn, "@4000")` ⇒ 0 ms ⇒ **~1200 `GET /orders/{id}` in 5 s**, unnoticed by the E2E.
  Fixed on the app side to `@(4000)`; the Pizza E2E now checks the polling rate.
  *Fixed (2.2):* Attribute values on non-string parameters are TS expressions according to the
  parameter metadata (`Count="5"` ⇒ `5`, `Interval="@4000"` ⇒ `4000`, `OnClick="Handle"` ⇒
  bound `EventCallback`); unknown parameters ⇒ TZS025, unknown types ⇒ warning TZS026.
  Conformance C12 ×4 green. The regression run found further silent strings in the apps
  (`size="20"`, `rows="3"`, `striped="true"` …).
- **C13** No named slots / `RenderFragment<T>` / `@context` / `Context=` / `TItem=` (codegen.ts:664-670) — slot tags are resolved as components.
  *Fixed (2.3):* The parent decides child-content elements from its
  parameter metadata — a direct child that names a `RenderFragment`/
  `RenderFragment<T>` parameter is a slot, even if a component of the same name
  exists (like Razor: child-content tag helpers bind before components); without
  parent metadata a tag stays a component/element.
  `@context`/`Context=` (component and slot) and implicit generic `ChildContent`
  without `<ChildContent>`; `Context` attributes of the `@typeparam`s (`TItem="Person"`) are
  consumed (the value must parse as a TS type). Diagnostics: TZS027/TZS028/TZS029 (unrecognized
  content, invalid child-content element, context name conflict), TZS025 for unknown
  slots and content-less components (with a rename fix); TZS024/TZS009 for
  type-argument values. All app components converted — no more handwritten
  render trees; 990/990 tests, E2E of all apps green. Open: `TItem` inference and
  typed contexts (2.4), LSP completion/hover for slots (2.5).
- **C14** Unquoted attributes: `<input type=checkbox disabled>` → `checkbox=""`, `type` lost (parser.ts:786-790).
- **C15** `@onclick:preventDefault="cond"` / `:stopPropagation="true"` produces a second handler (parser.ts:659-670). A modifier without a handler is an error (Blazor allows it).
- **C16** `@bind-Value:after/:get/:set` on components rejected (parser.ts:716-723).
- **C17** `@bind-Value="Model!.Title"` rejected — `isAssignableTarget` (codegen.ts:928) does not know `!.`. **77 % of all FluentCMS compile errors.**
- **C18** Method groups on other objects lose their receiver: `@onclick="item.toggle"` → is called with the component as `this` (event-callback.ts:48).
- **C19** Directives:
  - `@attribute` documented, but no codegen case (codegen.ts:140-173) → TZS001 **and** written verbatim above the class.
  - Multiple `@page` → the last one silently wins.
  - `@typeparam T where T : class` verbatim in `class C<…>`.
  - **`@namespace` / `@rendermode` / `@implements` / `@preservewhitespace` are rendered as content** (FluentCMS: `@namespace` in 160/217 files).
  - ~~Generic `@inherits Base<ICollection<T>>` → invalid import (FluentCMS: 24 files).~~ *Correction (Phase 0):* In the real plugin pipeline the workspace resolver resolves the generic name correctly (conformance tests green). The broken import only arose in the FluentCMS probe, whose resolver returned the name unchanged. Remaining: the compiler passes `Base<…>` untrimmed to `resolveType` — an unclean contract, not a user error.
  - `@page`/`@code` inside elements silently dropped or turned into render statements.
- **C20** `@:` lines do not process `@` transitions (parser.ts:200-208).
- **C21** A `buildRenderTree` written by hand in `@code` is silently overwritten by the generated (empty) one.

### Findings (medium/low)

- `<input></input>` → "Missing closing tag" (parser.ts:478/495); `<DIV>` as a component (parser.ts:469); `a < b` in text → TZS002; `{ json }` in component ChildContent → TZS003.
- `class="btn @(cond ? "on" : null)"` → `"btn null"` (Blazor: empty).
- Single-line blocks emit whitespace text frames per iteration.
- `@for (var i …) { <Row>@i</Row> }` — `var` in a deferred ChildContent lambda ⇒ all rows show the final value (emitting `let` solves this).
- Deviating `@foreach` headers (`Person p in people`, `var (k, v) in pairs`) → fallback + invalid TS.
- Source map columns in `@code` wrong (tabs → 2 spaces before column computation), `sourcesContent: null`.

### Positive

**Sequence numbers are correct:** compile-time counter (codegen.ts:335-345), deterministic,
bound to source position, loop iterations share numbers, branches have disjoint ranges,
ChildContent lambdas start in their own region at 0.

### Recommendation

1. **Replace `bakeMemberRefs` with TS-AST + scope analysis** (`ts.createSourceFile` —
   TypeScript is already a dependency). Only rewrite identifiers that actually are members
   (from the `@code` class body + base class via the checker); everything else stays free
   (import/global). Makes `knownGlobals` and the base-class workaround (port-findings C)
   unnecessary.
2. **Code-first parser in code contexts** (like Razor): TS statements via `ts.createScanner`,
   switch to markup on `<tag` in statement position, `@:`, `<text>`. Then
   `while`/`do`/`try`/`using`/fallthrough work without special nodes, locals are in scope, the
   brace pre-scan goes away.
3. **Line-aware code writer** (or magic-string with token mappings) for correct source maps.
4. **Diagnostic for every unknown `@word` at the start of a statement** and for `@` after
   alphanumerics — catches a large share of the silent errors. The documentation claim "never
   fails silently" is currently not true.

## 2. Type safety: no type check, no parameter metadata

- **T1** The build only strips types (esbuild `transformSync`, vite-plugin/src/index.ts:126). No `tsazor check` (backlog, handoff-2026-09-28.md:98).
- **T2** Component parameters are not checked — not even in the LSP: `b.addAttribute(1, "Name", 123)` with `unknown`. `<Greeter Name="@(123)" Nmae="typo"/>` → 0 diagnostics. The Fluent d.ts is `export const X: any`.
- **T3** The runtime silently discards unknown parameters (component-base.ts:67-76); Blazor throws.
- **T4** Cross-file types only when the other file is open in the editor (ts-service.ts / server.ts:79). False positive: `<Greeter @ref="g"/>` → TS2740.
- What the LSP catches: member typos in markup, errors in `@code`.

**Evidence from the fluentcms port** (both build green, both runtime errors):
- `apps/fluentcms-admin/src/RedirectToLogin.tsazor:6` calls `this.nav.navigateTo`, but the field is named `this.Nav` (`@inject NavigationManager Nav`, codegen.ts:258).
- The same file defines `buildRenderTree` in `@code` → it is overwritten by the generated empty one (C21) and renders nothing.

**Recommendation (highest leverage):** Extend the shadow modules from `packages/lsp` — typed
prop checking per component tag (e.g. `satisfies Partial<ParamsOf<Greeter>>`), shadows also
for closed files, a `tsazor check` CLI (+ optionally a Vite hook), real `.d.ts` per
component. The **parameter type metadata** is at the same time a prerequisite for C12
(static attributes, method groups), C13 (templated components) and `TItem` inference.

## 3. Runtime: diff and batching not faithful to Blazor

### Critical

- **R1 Changing `@key` recreates nothing** (diff.ts:358-394): a key miss falls through to sequence matching → the same instance gets `setParameters`, the same DOM element. Breaks "change the key = reset".
- **R2 Duplicate keys merge DOM** (diff.ts:358-366): two `<p @key=1>` → one `<p>`. Blazor throws.
- **R3 Components inside removed elements are never disposed** (dom-renderer.ts:374-381, 192-195). Leaks `addLocationChanged` subscriptions (NavLink, Router), EditContext, auth — leaked components render into detached DOM on every navigation. Same on a tag change. *Probably the most consequential bug in practice.*
- **R4 Moving a markup block/component only moves the comment markers** (dom-renderer.ts:557-564, 588-594). Currently masked by R8.
- **R5 `ShouldRender() === false` prevents the first render** (renderer.ts:196). Blazor always renders initially.
- **R6 Async lifecycle** (component-base.ts:40-46): `onInitialized` and `onParametersSet` are awaited, `stateHasChanged` once at the end ⇒ **no loading state**. Blazor renders while the task is still running, and again after it completes. `architecture.md` ("renders after each await section") and `port-findings.md` #3 ("does not render after the await", "Blazor behaves identically") are **both wrong**. The "stuck in loading" symptom from the Pizza port probably stems from fire-and-forget calls (*unverified*).
- **R7 Parent `onAfterRender(firstRender)` runs before the child render**: observed `P.render, P.after, K.render, K.after`. *Correction (B4): The core — `onAfterRender` before the child render — was a real bug. The order required in the test, "children before parent", is however not Blazor (there: render order, for a new subtree parent first), but a deliberate Tsazor choice.*

### High

- **R8 No parameter change detection** (dom-renderer.ts:298): every parent render re-renders the whole subtree, `OnParametersSet` fires every time. `attributeValueEquals` (diff.ts:416) is dead code.
- **R9 Render queue** (renderer.ts:187-226): order of insertion (child renders twice — *correction (B2): this matches Blazor's FIFO `ComponentRenderQueue`; parent-first is a deliberate Tsazor optimization, not Blazor semantics*); renders during flush → new microtask; a throw in `buildRenderTree` discards the rest of the batch (uncaught). No ErrorBoundary.
- **R10 Attributes** (dom-renderer.ts):
  - :432-435 handler set to `null` → listener stays active.
  - :453-456 `checked` as an attribute instead of a property → checkbox no longer syncs after a user click (affects `InputCheckbox`, `@bind` on a checkbox).
  - :197-198 `<select value>` set before the `<option>`s → initial value wrong (affects `InputSelect`).
  - :458-459 `name in element` assigns getter-only properties (`form`, `list`) → TypeError aborts the flush.
  - :465-476 removing `value` does not clear `input.value`.
  - :438 handler map lookup by attribute name vs. event name → listener is rebound on every callback change.
- **R11** Runtime `CascadingValue` ignores `Name` (components/cascading-value.ts:386-401).
- **R12** Cascading updates only flow through parameter re-sets (renderer.ts:125-147) → an intermediate component with `ShouldRender=false` stops the update.
- **R13** `disposeAsync` is never called (renderer.ts:150-165); children disposed before the parent. (FluentCMS: 44 usages.)
- **R14 Router** (route-data.ts):
  - :369-378 no precedence — `/users/{id}` beats `/users/new`.
  - :427 `^true|false$` ungrouped → `/f/trueish` matches `{b:bool}` (same for `regex(a|b)`).
  - :331 "True" matches, but converts to `false`.
  - No optional parameters (`{id:int?}`); `double`/`decimal`/`float`/`datetime` → `.*`; `long` via `parseInt` loses precision > 2^53; catch-all re-encoded.
- **R15** Navigation lock has no effect (navigation-manager.ts:42-78); `baseUri` ignores `<base href>`; `app.dispose()` (app.ts:173) removes neither DOM nor listeners.

### Medium/low

- `/^on/i` turns every function parameter with an "on" prefix (e.g. `onlyIf`) into an EventCallback and binds it to the wrong receiver (renderer.ts:14, 108). *Fixed (2.2, sync point B8):* heuristic removed, the compiler creates `EventCallback`s by parameter type.
- Global `activeRenderer` (dom-renderer.ts:27, 36, 520) → with two renderers `waitUntilIdle` misses handlers.
- Auth race: a late `getState()` result overwrites a newer notification (authentication-state-provider.ts:273-281).
- EditForm: `onValidSubmit` neither awaited nor tracked; no `OnSubmit`/`OnInvalidSubmit` (edit-form.ts:173).
- DI without scoped lifetime and without cycle detection. `Dispatcher` unused, `isRenderingInProgress` always false.

### Performance

- One insert moves all following siblings (dom-renderer.ts:577): 1 insert at the front of a 100-item list = 101 `insertBefore`. **Loses focus in the process** (verified), probably also iframes/video/animations.
- `getFrameChildren` 3× per element and render, plus 4 maps, 2 sets, 1 array per element.
- `findParameterMetadata` builds a map over the prototype chain on every `setParameters` (renderer.ts:113, component-base.ts:50) — with R8 for every child on every parent render.
- No O(n²) in the diff itself.

### Recommendation

1. **Port `RenderTreeDiffBuilder` faithfully:** ordered two-pointer walk, key dictionary only as a fallback, error on duplicate keys. Fixes R1, R2 and the move costs.
2. **Logical node range abstraction** (start/end, moves as a unit, removal walks the subtree and disposes). Fixes R3, R4.
3. **Real render queue with end of batch:** parent-first, `OnAfterRender` after the whole batch, first render ignores `ShouldRender`, errors isolated per component → basis for ErrorBoundary.
4. **Mind the order:** build R8 (change detection) only after or together with R4 and R12 — R8 masks both.
5. **Lifecycle conformance test suite** that pins down Blazor's semantics (see also §7 documentation drift).

## 4. Import resolution by heuristic (vite-plugin / workspace)

- **I1** `knownGlobals` (vite-plugin/src/index.ts:78-81) matches every word that occurs in `RUNTIME_TYPES`: `@Parameter() Token` + `@Token` → `import { Token } from "@tsazor/runtime"` (type-only export ⇒ link error). PascalCase parameters are Blazor convention; `RouteData`, `EditContext` collide.
- **I2** Imported names in markup get a `this.` prefix: `@Status.Open` (enum from `utils.ts`) → `this.Status.Open`. Lowercase functions/constants are never imported.
- **I3** Default vs. named import guessed from the file name (resolver.ts:247-250). `plugin.test.ts:101` expects `import CounterService from …` against a fixture with `export class CounterService {}` (line 54) — the test locks in a link error. The fluentcms port defensively adds `export default FluentAuthProvider`.
- **I4** As soon as a bare `@using` (npm package) is in scope, every tag name is assumed to be exported there (resolver.ts:242-243, 268-270) → `<Buton>` gets no TZS005. With `@tsazor/components` + `@tsazor/fluent` the first source silently wins for shared names (Button, Card, Alert, Table, Tabs, Pagination).
- That false positives mostly do no harm is only because esbuild removes unused imports — fragile, not safe.

**Recommendation:** allow real top-level `import` statements in `.tsazor` (analogous to Svelte
`<script module>`), or resolve free identifiers via the TS checker in the shadow; report
unresolved/ambiguous names as errors.

## 5. Tooling, packaging, component libraries

### HMR / invalidation

`vite-plugin/src/index.ts` has no `handleHotUpdate`, no watcher, no `addWatchFile`/`invalidateModule`:
- a newly created component → the dependent file stays on TZS005 until the next edit,
- a `_Imports.tsazor` change re-transforms nothing,
- adding/removing `.tsazor.css`/`.tsazor.ts` has no effect (`docs/scoped-css.md` claims the opposite),
- new `@page` → manifest stale (documented).

### Packaging (tested externally via tarball)

- `tsc` with `moduleResolution: bundler` emits extensionless imports ⇒ externally `vite build` works, but **Vitest + `@tsazor/testing` fails** (`Cannot find module …/dist/render-tree/render-tree`); `compiler`/`workspace`/`lsp` cannot be loaded directly in Node. Fix: `module: NodeNext` + `.js` extensions or bundle per package.
- No shipped ambient types for `*.tsazor` / `virtual:tsazor-routes` — four apps copy `src/types.d.ts`, all components typed as `ComponentBase`. Proposal: `@tsazor/vite-plugin/client`.
- `components`/`fluent` without a `types` export, d.ts is `any`.
- `packages/vscode/package.json` does not list `@tsazor/lsp`/`@tsazor/workspace` ⇒ **a clean `pnpm -r build` fails** on vscode.
- `vite-plugin` bundles compiler+workspace but lists them as dependencies. No package has a `license` field.

### LSP

The design is right (v2: one `ts.LanguageService` over virtual shadow modules, v1 regex as fallback). Limits:
- only `workspaceFolders[0]` with its tsconfig — in the monorepo the root solution tsconfig (`files: []`) (ts-service.ts:105-127, server.ts:290); differs from the Vite root for `_Imports`,
- no `didChangeWatchedFiles`, no re-checks of dependent open documents,
- diagnostic ranges 1 character wide.

### Windows paths (*unverified*)

`workspace/src/imports.ts:114` compares `current.startsWith(stop)` case-sensitively —
a drive letter/case mismatch between `config.root` and the module ID would stop the
`_Imports` walk after the first folder. `routes.ts` scans the whole project root
(incl. `test/`, `wwwroot`) instead of only `src`.

### Fluent

- `Button` declares `ariaLabel`/`ariaDescribedBy` but does not render them (Button.tsazor:1) → icon buttons without an accessible name; no `@attributes` pass-through (`data-testid`, `aria-*` get lost).
- TextInput/Select/Checkbox without `id` → `label for` null; all message IDs `fui-input-message` → duplicate IDs, broken `aria-describedby`. Every field message is `role="alert"` (loud).
- Enum-like parameters as `string`, inconsistent vocabulary ("medium" vs "m"); camelCase instead of PascalCase (the runtime matches case-insensitively, the LSP suggests camelCase).
- Solid: Dialog, Tabs, Toast (focus trap, roving tabindex, `aria-live`).

### Test gaps

vite-plugin 19 tests in one file, workspace 6, components 22. Not tested:
invalidation/HMR, Windows paths, full `vite build`, import inference false positives/negatives,
package consumption from outside. The plugin test fixture contains C# (`private string summary = "Sunny"`).

## 6. FluentCMS as a compatibility measurement

**Setup:** FluentCMS is a Blazor Web App — static SSR, `InteractiveServer` per
component (26 `@rendermode`), cookie auth via `HttpContext` (37 places / 9 files),
catch-all `@page "/{**Route:nonfile}"`, plugins via `DynamicComponent`. 172 files have
`.razor.cs` code-behind, only 1 `@code` ⇒ markup findings are cleanly separated from C#, and
Tsazor's `X.tsazor.ts` model fits directly.

**Mechanical run** (parser + codegen over all 217 files):
- 171/217 without a diagnostic; 180 errors in 46 files; 0 crashes.
- After subtracting the silent miscompilations: **only 17/217 actually correct**; with `@namespace` ignored it would be 103.

## 7. Strategic

1. **Type checking is the core of the .NET promise.** A .NET developer expects
   `dotnet build` to fail on `<Greeter Name="@123"/>`. The machinery largely exists
   in the LSP (§2).
2. **Templated components are the biggest parity gap** — they block an idiomatic
   `App.razor` (`<Found>`), every DataGrid, and today force handwritten
   `RenderTreeBuilder` code (gallery Table `rowContent`, fluentcms `App.tsazor`). More important
   than new components.
3. **The .NET bridge is not yet a framework feature.** Every app invents its own:
   Sleipnir (external `sleipnir-codegen`, all properties optional for lack of nullability),
   FluentCMS (hand-copied DTOs, envelope repeated per method, `openapi-typescript` script
   present but unused; `TsazorHttp` throws on `!ok` before the envelope is readable),
   Pizza (handwritten REST). An official package — OpenAPI → TS client + nullability
   + ProblemDetails/envelope errors + DataAnnotations → validators — would be the actual
   unique selling point.
4. **Packaging is not ready for external users** (§5).
5. **Documentation drift:** lifecycle (`architecture.md` vs. `port-findings.md` #3 vs. code),
   HMR/sidecar invalidation (`scoped-css.md`), `@attribute` (`language-reference.md`),
   "never fails silently". A conformance test suite should pin down Blazor semantics.
